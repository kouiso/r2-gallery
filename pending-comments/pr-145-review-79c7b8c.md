## must

**M1. 完了した行が台帳に「転送中」のまま戻ることがあり、再起動すると重複してアップロードされる（この PR で入った退行）**

`_run` の流れが変わりました。

- 修正前: `_completing.remove(t)` の直後に、同期で `status = done` にしていた。
- 修正後: `_completing.remove(t)` の後に `await _dropStaged(t)` があり、`status = done` はその後。

このため、`_completing` から外れたのに、まだ done になっていない時間ができます。その間に別の行の `_persist()` がスナップショットを取ると、この行は `status: running` で台帳に書かれます。`_persist()` の除外条件は `_completing` に含まれるか `status == done` で、どちらにも当てはまらないからです。

`_dropStaged` は `stagedPath` を先に null にします。そのため台帳には `stagedPath` がなく `sourcePath` だけが残り、次の起動では「退避の途中で落とされた」行として退避からやり直します。#121 の後は、この再送が 409 になり `name (2)` で上がります。これは `_persist` のコメント（「2 件が続けて終わった時、後の行の書き込みが前の行を『転送中』のまま書き戻さんようにする」）と、既存のテスト「2 件の完了が重なっても、先に終わった行を台帳へ書き戻さない」が守っている性質そのものです。

再現手順（使い捨てのテストで確認し、コミットはしていません）:

1. 既存テスト「2 件の完了が重なっても…」の hold の仕組みに、この PR の `_SlowDeleteOverrides(800ms)` を組み合わせる。
2. a の PUT を放し、a の `stagedPath` が null になる（削除待ちに入る）まで待つ。
3. b の完了要求を放す。
4. 両方の行が done になった後、`q.idle()` まで待つ。

条件と根拠:

- 起きるのは、退避ファイルの削除中に別の行が書いた台帳が、その時点で最後の書き込みになった時です。テストの 800ms は人工的な値です。
- ただし、この PR の前提は「負荷が高いと delete が遅れる」ことで、その時間はそのまま危険な時間になります。
- 削除の時間中の一時停止・取り消し（行はまだ active で、`_completing` からも外れている）でも同じように古い行が残りうると考えています。ただしこちらは試していません。

修正案: 削除と done への変更を `_completing` の中に入れる。

```dart
_completing.add(t);
try {
  await _persist();
  // 退避ファイルを消し終えてから完了にする。終わるまで台帳の書き込みからは外したままにする
  await _dropStaged(t);
  t.status = TransferStatus.done;
  t.loaded = t.size;
} finally {
  _completing.remove(t);
}
if (!_done.isClosed) _done.add(t);
```
