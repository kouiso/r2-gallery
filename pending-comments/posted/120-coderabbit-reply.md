The ordering part is fixed at 01936fb: the record is written before the file move and before `mutateAlbums`; a failed put aborts with nothing removed, and a failed move deletes the record.

One window remains and is accepted on purpose. The record is built from a read of albums.json taken before the move. If, between that read and the `mutateAlbums` commit, the same item is added to another album, and then the rewrite of the record also fails (or the Worker stops right there), only that late-added membership is lost on undo; the file itself and every other membership are restored. Closing it fully would need either a second record write before the albums commit (still not atomic with R2) or moving the record into albums.json itself, which would make the record depend on the purge change planned in #51. The trigger needs one user to add the same photo to another album within a few milliseconds of trashing it, and the failure is a missing album entry that can be re-added by hand, so the cost of the extra machinery is higher than the risk.
